返工通常从这六个地方开始。

先查清是哪一处出了问题，再决定用哪个 skill。

  • 需求没写清需求里没有边界和验收条件，代码已经改了一半。
  • 结果没有命令可复查回复里只写“已完成”，没有测试命令、输出或失败项。
  • 只消掉报错异常不再出现，但数据路径和 root cause 仍没查清。
  • UI 只对上截图input、tab、select 和 button 还没有真实状态与交互。
  • 接口列表缺类型只摘 endpoint，schema、DTO 和复用 type 没跟上。
  • diff 混进别的改动commit 前才发现临时文件、无关格式化或未验证代码。

通常怎么做：先把需求说清，再写代码。

复杂改动先补 plan。实现或修复完成后，运行验证命令，再看 diff 是否能提交。

  1. 需求

    dev-grill-docs
    dev-design-context

    确认术语、边界和验收条件；做 UI 时先补设计上下文。

  2. 方案

    dev-plan

    改动复杂或风险高时，再写文件范围、取舍和验证命令。

  3. 实现 / 修复

    dev-tdd
    dev-fix

    新功能先写失败测试；bug 先复现，再追 root cause。

  4. 验证

    dev-verify

    运行本次改动需要的命令，原样记录通过项和失败项。

  5. Review / 收尾

    dev-code-review
    dev-finish

    看完整 diff，确认没有夹带，再决定 commit、PR 或合并。

拿不准下一步时，用 dev-auto 判断当前阶段。其他 skill 仍由你明确调用。

先查全 endpoint 和 type，再写调用代码。

把 Swagger UI、OpenAPI、Knife4j、FastAPI docs 或 Redoc 的地址贴进来。结果包含 module、endpoint、请求响应和可复用 type/schema，需要时可导出 Markdown 或 JSON。

  • 当前 chat 只复用这个已确认的 source。
  • 如果给了多个 source，先问清楚用哪一个。
  • 只有明确传入 --config 时才读配置。
  • token、cookie 和 Authorization 不写进输出。
